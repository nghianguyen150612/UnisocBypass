## Read-only collection and evidence discipline

1. Start with authorized owner/vendor records and a matching stock package, if available. Record source, date, model, build, acquisition tool and byte count. Redact personal data; preserve originals externally, read-only. The package and hardware are not required to finish this P003 report.
2. Hash the package and every original component on acquisition and after transfer; associate each report with its hash, slot, partition and provenance. P001's `inspect_uboot_ums9620.py` can report structural bounds, SHA-256 and explicitly limited observations against a copy, without defaulting a target load base. A parse or hash match does not prove RSA, acceptance, execution or device identity [A6]. Manually investigate unexpected/ambiguous fields; don't force them into a known variant.
3. For an authorized external FDL profile, use P002's `fdl_qualify.py` inventory only. An explicit, unique settings-linked pair can be **unverified**, not compatible. Missing, conflicting or malformed references stay insufficient; a definite referenced-file defect is structurally incompatible [A8]. The public Z2352N support listing is not proof of a loader hash, address, board initialization or authenticated storage access.
4. Separate persistent state, U-Boot output, AVB results, trusted-firmware state and presentation when collecting evidence. Record unknown or error values as such. Any hardware access, device-state experiment, image modification, flash or restore requires a separately defined future phase and explicit approval; do not perform it as an inference from this matrix.
